## What

Mantaq is a state machine library for TypeScript. You model a flow, a
checkout form or an order pipeline or a game, as states and the events that move
between them. Mantaq runs the machine: it tracks where the flow is, fires
transitions, runs side effects, and cleans up after itself.

## Why

Multi-step flows are hard to keep correct in plain code. Booleans, nested
conditionals, and a `currentStep` variable drift apart as the flow grows, and
there is no compiler help when you forget a branch. A state machine makes the
flow the source of truth: every state and every possible transition is declared
up front, typed, and testable.

Reach for Mantaq whenever you have a flow with a known set of steps and clear
transitions between them. It is not a general-purpose state container. It
models _where a process is_, not every piece of data your app holds.

## Core ideas

- **Actor.** One running state machine. Holds the current state, context,
  effects, transitions, and clock.
- **State.** A node in the flow. A state can be marked final.
- **Event.** A typed message. Events trigger transitions.
- **Effect.** Code that runs on state entry and aborts on state exit.
- **Context.** The data the machine carries. Survives transitions.

## Packages

| Package             | What                                                                                                                         |
| ------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| `@mantaq/core`      | Runtime. `Actor`, `state`, `event`, `VirtualClock`                                                                           |
| `@mantaq/sugar`     | Helpers. `matches`, `states`, `events`, `tag`, `isIn`, `activeLeaves`, `ActorMap`, `broadcast`, `withPromise`, `withTimeout` |
| `@mantaq/test`      | Test harness and coverage assertions. `createTestHarness`, state/transition/effect assertions                                |
| `@mantaq/traversal` | Graph building, instrumentation, history, and graph algorithms. `buildGraph`, `instrument`, `History`                        |

## The docs story

The whole docs build **one example**: a multi-step checkout form.

The buyer fills in basic info, a shipping address, and payment details. The
system charges the card and shows the result. Every page adds a piece to the
same machine.

```
basicInfo → payment → success (final)
```

Later pages add more states, more events, effects, and testing.

## Quick example

The checkout form, cut to bone: three states and two events.

```ts
import { Actor, state, event } from "@mantaq/core";

const basicInfo = state("basicInfo")();
const payment = state("payment")();
const success = state("success")().final();

const submitBasicInfo = event("submitBasicInfo")();
const submitPayment = event("submitPayment")();

const checkout = new Actor({
  inputs: [submitBasicInfo, submitPayment],
  states: [basicInfo, payment, success],
  initial: basicInfo,
  setup: (m) => {
    m.on(basicInfo, submitBasicInfo, () => ({ state: payment }));
    m.on(payment, submitPayment, () => ({ state: success }));
  },
});

checkout.send(submitBasicInfo.create());
checkout.snapshot().path[0]; // "payment"
```

`success` is final. The actor stops there, and entering it fires the `"done"`
subscribers.

:::tip[Sugar exists]
Core is verbose on purpose. It shows what happens under the hood.

`@mantaq/sugar` has helpers: `matches(checkout, "payment")` instead of
`snapshot().path[0] === "payment"`. Batch creation, effect helpers, state
grouping.

Learn core first. Sugar second. You'll know _why_ each helper exists.
:::

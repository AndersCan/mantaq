## What

Every `m.on` and `m.onAny` lists its targets in `to`. The builder records them,
so the whole transition graph is static data: it can be drawn without running
a single handler.

The diagram below is the docs' checkout machine
([`checkout.ts`](https://github.com/anderscan/mantaq/blob/main/apps/docs/src/content/docs/checkout.ts)),
generated when the site is built. It cannot drift from the code.

## Reading it

- **Box**: a state. Double border: final.
- **Arrow**: one target from one `to` list, labelled with its event.
- **Dot and arrow on the left**: the initial state.
- **Dotted arrow, italic label**: an internal event, emitted by an effect.
- **Faint self-loop**: the effects the state runs on entry, by name (`runs chargeCard`).
- **Dashed box `*`**: an `onAny` registration, meaning any non-final state.

Click a state or an edge, or focus it and press Enter. The panel shows the
handler behind an edge: where it is registered, which branches lead where,
and what it reads and writes in context.

## Walking it

The panel runs the real machine in your browser, on a virtual clock, without running its effects. It starts
in the initial state, and the pulsing edges are the steps you can take next.
Click one, or use the **Step** tab:

- **Send**: every event the current state handles, plus the inputs it ignores.
  An event that carries a payload asks for one first, in a form at the
  bottom of the viewer, already filled. Change a field, pick other values, or
  edit it as JSON, then Send.
- **Time**: pending timers. Advance the clock to fire one, or by any number of
  milliseconds.

Because the handlers run, guards are evaluated: you only go where the code
really goes. The **Context** tab shows the machine's data after each step, with
the lines the step changed marked. **Path** lists the steps so far; **Back**,
**Reset** and the path list undo them by replaying from a fresh actor.

Effects do not run in the panel. Entering `submitting` starts `chargeCard`;
the panel waits instead and offers what it reports: `paymentOk`, `paymentFail`
or `paymentTimeout`. Pick one to say how the charge went.

## A bigger machine

The checkout is a straight line. The saga orchestrator
([`saga.ts`](https://github.com/anderscan/mantaq/blob/main/apps/docs/src/content/docs/saga.ts))
is closer to real work. An order runs through inventory, payment, shipment and
notification. Each step is an effect that reports back. When a step fails, the
saga undoes the finished ones in reverse: refund the payment, then release the
inventory. `CANCEL` is an `onAny` handler, so it works from any state, drawn
from the dashed `*` box.

### Coverage from fuzzing

The diagram is built from the `to` lists, so it shows what each handler
_declares_. The docs build also fuzzes the machine: it sends thousands of
seeded event sequences to a real actor and records which states and edges they
actually reach. Pick **Coverage from: fuzz runs** to dim everything no run
reached.

Here one edge stays dim: `compensatingRefund` → `failed` on `REFUND_DONE`. The
handler lists both `failed` and `compensatingRelease` in `to`, but it only goes
to `failed` when no inventory was reserved. A refund only happens after a
payment, and payment only starts once inventory is reserved, so that branch
never runs. The declaration is not wrong, only wider than the machine needs.
Click the edge: the panel says so.

Fuzzing is not proof. A dim edge was not reached, which is not the same as
impossible. Read the handler before deleting anything.

## A machine that decides with its context

In the checkout and the saga, context mostly records what happened. In the
login lockout
([`login.ts`](https://github.com/anderscan/mantaq/blob/main/apps/docs/src/content/docs/login.ts))
context decides where the machine goes next. It counts wrong passwords. After
a rejection the handler reads that count: below three, back to the form; the
third in a row, `lockedOut`. Each lockout also counts, and the next one lasts
twice as long.

The states are what the person sees: the form, a pending check, signed in,
locked out. The data the check needs (username and password) and the signed-in
user ride on state payloads, so context holds only the counters.

<Machine src="src/content/docs/login.ts" />

Try it: send `SUBMIT` with a wrong password (the form starts filled; `ada` / `lovelace` is the account that works). `checking` starts a
300 ms timer: advance it in the **Time** section, and you are back at the form.
Open the **Context** tab: `failedAttempts` went up by one. Do it twice more and
the third rejection goes to `lockedOut`, with a 30 s unlock timer. The diagram
draws both targets of `REJECTED`; the count in context picks one.

Fuzzing finds the lockout too. A single extra `REJECTED` is not enough, since
the form ignores it: the fuzzer repeats the whole cycle that bumped the count,
`SUBMIT` then `REJECTED`, until the guard flips.

## Draw your own

Add the Vite plugin from `@mantaq/inspect` and keep the page open while you edit:

```ts
// vite.config.ts
import { mantaqViz } from "@mantaq/inspect/vite";

export default defineConfig({
  plugins: [mantaqViz({ machines: "src/**/*.machine.ts" })],
});
```

Then open `/__mantaq/` on the dev server. It redraws on save and keeps your walk. `vite build` writes the same page as a static site under the same path.

### Publish it with Astro

To put the diagram on a page next to your prose, use the Astro integration. List the machine files once in the config, then add one component per machine:

```js
// astro.config.mjs
import { defineConfig } from "astro/config";
import { mantaqViz } from "@mantaq/inspect/astro";

export default defineConfig({
  integrations: [mantaqViz({ machines: ["src/machines/checkout.ts"] })],
});
```

```astro
---
import Machine from "@mantaq/inspect/astro/Machine.astro";
---
<Machine src="src/machines/checkout.ts" />
```

`astro build` renders the design findings above the diagram and bakes in the live panel. A file missing from `machines`, or one that cannot load, fails the build; findings do not, unless you pass `failOnFindings: true`: then `astro build` also fails on any design finding, a machine that could not be fuzzed, or an expectation that is not checked, listing each with the events that lead there. `astro dev` is unchanged.

## What it does not tell you

Guards are not evaluated. An edge means the handler _may_ go there, not that it
ever will. A handler with no `to` can only stay in place.

When the target depends on the current state, register one `m.on` per state
instead of branching on `actor.state` inside `onAny`. Each `back` above is its
own edge for that reason. See [`onAny`](/mantaq/core-concepts/events/#onany).

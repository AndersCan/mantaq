`createPool` builds one inbox and `n` workers that pull work. Boxes are machines, arrows are events, and `workers ×3` is three actors drawn once, one dot each.

## Try it

1. Read the diagram: work enters at **from outside** and goes to `teamInbox`, which is `empty`. `workers ×3` shows three open dots: all free. One arrow runs from the inbox to the workers (`ITEMS_ASSIGNED`) and one runs back (`ITEMS_FINISHED`, `ITEMS_FAILED`, `ITEMS_RETURNED`). The line under the diagram reads `events: team.*   ○ free  ● working`.
2. On the Step tab, send `team.ITEM_ARRIVED`. The dot for `w1` fills, the `ITEMS_ASSIGNED` arrow turns pink, and the step line ends `then w1: free → working`.
3. Send three more. `teamInbox` reads `holding`: that is where work waits. All three dots are filled.
4. In w1's Send list, press `team.RUN_SUCCEEDED`. The inbox hands w1 the waiting item, so `teamInbox` reads `empty` and the three dots stay filled.
5. Click the `ITEMS_ASSIGNED` arrow. Details names who sends it and the states that take it. **Open workers at free** jumps to the worker's diagram at that arrow; **← System** comes back.
6. On the Path tab, pick the run `Four items, three workers`. It ends at `holding` with three filled dots.

`run` gets the items and resolves when they are done. If it rejects, the items go back to the front of the inbox. `keep: "set"` drops an arrival whose key already waits, and `batch: Infinity` hands a worker everything that waits: use both when a second request for the same thing adds nothing.

## Why the diagram looks like this

| You see                                     | Why                                                                                                                                                                               |
| ------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| One dot per worker, not three boxes         | The workers are an actor map: one box, and one dot for each worker that is running. Open is free, filled is working. A hand-written copy per worker is three boxes, so use a map. |
| Arrows between boxes, not loops on a parent | A parent that only forwards events draws self-loops and hides the receiver. Wire the parts in the factory.                                                                        |
| A busy worker sent work sends it back       | `team.ITEMS_RETURNED` puts the items at the front of the inbox. Nothing is dropped.                                                                                               |
| Map arrows show no hit count                | The fuzzer does not send to map children, so the arrows to `workers ×3` have no hit count. Run the steps by hand to see them fire.                                                |

## Limits

- The queue lives in memory and is lost on restart.
- It has no size limit.
- Each pool needs its own `name`: the name prefixes every event id, so two pools with one name share ids.

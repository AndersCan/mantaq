# Atlas Phase 5: does AST guidance help the fuzzer?

Generated by `vp run atlas:compare` (30 seeds, 2000 iterations, seeds 1..30). Iteration counts are deterministic for a given seed; the `ms/run` column is wall time on the author's laptop and is not.

## Arms

| arm        | adds                                                                                                                                 | from              |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------------ | ----------------- |
| `no-loop`  | nothing: Phase 3 mutation (insert / delete / swap / payload / advance)                                                               | —                 |
| `blind`    | **loop**: repeat a step that changed the actor's context 2–13 times                                                                  | runtime only      |
| `literals` | + literal seeding: compared literals and `L±1` offered to payload mutation and as loop counts                                        | AST `literals`    |
| `distance` | + branch-distance guide on payload **and context** comparisons: a run that gets closer to an unseen side is kept as a stepping stone | AST `comparisons` |
| `guided`   | `literals` + `distance` (what `atlas:export` uses)                                                                                   | both              |

"Handler outcomes" = distinct `edge:` / `stay:` / `error:` features. "All features" adds `state:`.

## Verdict

- **Counters need the loop.** `retry` locks out on `attempts > 10` (context). Without looping, no seed reaches `lockedOut` in 2000 iterations (no-loop: 3.0 outcomes, flat). With looping, every seed does (5.0): median first hit 131 iterations blind, 61 with literals (loop count 11 straight from `10 + 1`) or with distance (each extra `failed` moves `attempts` closer to 10), 55 with both. Looping only steps that changed context keeps it from padding runs with no-op repeats.
- **Real examples (checkout, auth, saga): no measurable effect** from any arm. Their branches read actor state (`checkout.back`) or context set once (`saga.completedSteps`), and no counters. The differences are random-stream noise, within one standard error (sd ≈ 2–4 outcomes, n = 30). The loop operator spends ~20% of mutations on repeats, which shows up as slightly slower mid-run coverage on saga and checkout (e.g. checkout at 250: no-loop 8.5, blind 7.5), with the same end coverage. One `guided` seed on checkout ends one edge short at 2000.
- **Credit: literal seeding is decisive**; looping costs it. `manualReview` needs `amount > 50000` from a sample of `1000`. Without literals it is not reached in most seeds. Literals reach it at a median of 170 (122 before looping existed), guided at 106 (61 before). The loop budget goes to repeating `setTier`, which changes context but leads nowhere.
- **Branch distance alone** helps only when progress is incremental: a lot on `retry` (each loop step closes the gap), nothing on `credit` (payload mutations jump, they don't walk).
- **Cost:** per-run time is unchanged to ~1.2× on the examples and credit, and 2× on retry (13 → 26 ms: longer looped runs). It is still milliseconds.

## Recommendation

Keep the AST layer and literal seeding. Keep looping: it is the only arm that unlocks counter-guarded branches, which are common in real machines (retries, attempts, budgets). Its cost is a modest slowdown elsewhere. Keep branch distance now that it reads context comparisons too: that is where it pays off.

Caveat on evidence: `credit` and `retry` are fixtures written to have far literals and counters. The three real examples show no benefit from any arm. Treat those two as "the mechanism works", not "typical machines benefit".

## Tried and removed: learned operator schedule

A deterministic bandit (after AFL's MOpt) picked mutation operators by their smoothed rate of producing kept runs, instead of fixed weights. Same 30 seeds, on top of `guided`:

| variant                    | checkout end | auth end | saga end | credit → manualReview | retry → lockedOut |
| -------------------------- | -----------: | -------: | -------: | --------------------: | ----------------: |
| fixed weights (`guided`)   |         10.9 |     14.0 |     18.4 |                   106 |                55 |
| bandit, uniform prior      |         10.9 |     14.0 |     17.1 |                   107 |                41 |
| bandit, fixed-weight prior |         11.0 |     14.0 |     18.1 |                   162 |                40 |

"end" = handler outcomes at 2000 iterations. The other columns are the median iteration of first hit.

The bandit is faster on `retry`, worse on `saga` (uniform prior) or `credit` (fixed-weight prior), and within noise on the rest. A run keeps only ~10–20 children, which is too little reward to learn from, and credit assignment to 1–3 stacked operators is coarse. It doesn't beat fixed weights, so it was deleted. This is the measured answer to "can a GA/RL learner do the testing": on machines this size, what blocks coverage is missing information (constants, counters, payload shapes), not the choice of search policy.

# Atlas Phase 5: does AST guidance help the fuzzer?

Generated by `vp run atlas:compare` (30 seeds, 2000 iterations, seeds 1..30). Iteration counts are deterministic for a given seed; the `ms/run` column is wall time on the author's laptop and is not.

## Arms

| arm        | what it adds over Phase 3                                                                                                                             | from              |
| ---------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------- |
| `blind`    | nothing: Phase 3 coverage-guided fuzzing                                                                                                              | —                 |
| `literals` | literal seeding: every literal a handler compares against (and `L±1`) is offered to payload mutation                                                  | AST `literals`    |
| `distance` | branch-distance guide: a run that moves a payload value closer to an unseen side of a `payload.x <op> literal` comparison is kept as a stepping stone | AST `comparisons` |
| `guided`   | `literals` + `distance` (what `atlas:export` now uses)                                                                                                | both              |

"Handler outcomes" = distinct `edge:` / `stay:` / `error:` features (each handler return path actually taken). "All features" adds `state:` features.

## Verdict

- **Real examples (checkout, auth, saga): no measurable effect.** Their handlers branch on live actor state (`checkout.back`) or context (`saga.CANCEL`, `REFUND_DONE`), never on payload-versus-literal comparisons. `distance` is byte-identical to `blind` (nothing to measure, so it never keeps a run). `literals` differs only because string literals compared against actor state (`"payment"`, `"inventory"`) enter the string pool and shift the random stream. Differences are within one standard error (sd ≈ 2–3 outcomes, n = 30). All arms reach the same final coverage on these three.
- **Credit (synthetic, built for this comparison): literal seeding is decisive.** `blind` never reaches `manualReview` (it needs `amount > 50000` from a sample of `1000`; blind numeric mutation is ±1, ×2, ÷2 or uniform in ±1000) in more than half the seeds within 2000 iterations. `literals` reaches it at a median of 122 iterations, `guided` at 61.
- **Branch distance alone barely helps** (credit: 5.3 vs 5.0 outcomes at 2000). The stepping stones it keeps still have to be mutated by doubling, which takes several lucky picks in a row. **On top of literals it halves time to the hard edge** (61 vs 122 median iterations) and makes every seed reach full coverage by 1000 (8.0 ±0.0 vs 7.9 ±0.5).
- **Cost:** none that matters. ms/run is within noise across arms; the AST pass itself is ~150–250 ms per file, once per export.

## Recommendation

Keep the AST layer. Its main value is the explanation (branches the probe cannot see, live-state reads, not-analyzed reasons), and literal seeding is a cheap side benefit with a real effect when handlers compare payload fields against far-away constants. Keep branch distance only because it is ~100 lines and composes with literals. If code budget matters, it is the first thing to remove: alone it does not pay for itself.

Caveat on evidence: the only machine showing a benefit is one I wrote to have far literals. The three real examples show none. Treat the credit numbers as "the mechanism works", not as "typical machines benefit". Payload-comparison-heavy machines (validation, thresholds, pricing) are where to expect it.
